## 1. 架构目标与约束

### 1.1 目标

1. **以最小工程量支撑 MMVP 三大假设验证**（内容留存 / 搭子需求 / 应征信任），4-6 周内可上线
2. **平滑演进到 v1**（圈子/活动/支付/IM），MMVP 的接口与数据模型不做推倒重来
3. **满足微信 UGC 合规硬约束**：内容安全检测、举报机制、企业主体

### 1.2 硬约束

| 约束 | 来源 | 架构应对 |
|---|---|---|
| 小程序请求域名须 HTTPS + ICP 备案 + 白名单 | 微信平台规范 | 复用已备案域名 meetpoint.top，新服务以路径前缀挂载，零新增备案/证书工作 |
| UGC 必须接入内容安全检测 | 微信平台规范 | 服务端统一封装 `msgSecCheck` / `mediaCheckAsync`，发布链路强制经过 |
| 应征联系方式仅发起人可见 | PRD 4.4 隐私红线 | 敏感字段存储隔离 + 服务端鉴权输出 + 数据库唯一索引（见 §6.3） |
| 位置/联系方式等个人信息最小必要 | 《个保法》 | **不采集实时定位坐标**；定位授权仅用于默认城市推荐（城市粒度）；搭子帖地点为用户主动选择并公开的 POI 名称（见 §7） |
| 个人主体不可上架 UGC 社区 | 类目规则 | 需企业主体 + 对应类目资质（运营前置，不阻塞开发） |

```

│   message / seccheck / admin / upload      │
│              ↓                             │
│  ┌──────────┴──────────┐                   │
│  ↓                     ↓                   │
```

读图主线：**前端 → Nginx → Express → MongoDB/本地媒体 → 微信开放能力**；定时任务与主服务同进程（node-cron）。

### 2.2 技术选型与理由

| 层 | 选型 | 理由 | 放弃项 |
|---|---|---|---|
| 前端 | 微信小程序原生（现状延续） | 已有 15 页实现；无跨端需求 | uni-app/Taro |
| 后端 | **腾讯云服务器自建 Node/Express** | 复用已验证的部署形态（meetpoint 同栈同机）；域名/证书/备案/白名单全部现成；无冷启动；v1 的 IM（WebSocket）、支付回调、定时任务全部直路演进；服务器已付费沉没成本再利用 | 微信云开发（access_token/回调配置更绕，长连接不支持，为 v1 IM 留坑） |
| 数据库 | MongoDB（服务器已装，独立 database） | 帖子/评论天然文档结构；运维零新增；已有连接模块实践（`db.js`） | MySQL |
| 反向代理 | Nginx（存量） | HTTPS 卸载 + 静态媒体直出 + 未来 WebSocket upgrade | — |
| 进程守护 | PM2 | 单机标准实践，开机自启 + 崩溃重启 | Docker（单服务收益低，v1 服务多了再容器化） |
| 媒体存储 | 服务器本地磁盘 + Nginx 静态直出 | MMVP 量级够用；CDN/COS 之后再挂 | 腾讯云 COS（MMVP 期增加密钥管理与迁移成本，列为 v1 增量） |
| 部署 | `deploy.sh`（rsync + pm2 reload，沿用存量脚本模式） | 已有肌肉记忆，无需 CI 系统 | GitHub Actions 等（v1 再上） |

**从云开发改为自建的决策说明**：v1.0 设计曾选云开发以换取免运维，但团队已有可用的腾讯云服务器与全套备案/HTTPS 设施（沉没成本），且 v1 规划中的 IM 长连接、支付回调、复杂定时任务均为云开发短板。自建方案在 MMVP 期增加的运维面（备份/监控）在 §8 已给出最小配置。

### 2.3 媒体存储预算模型

增长公式（替代拍脑袋总量）：

```
日增存储 = 日发帖数 × 户均媒体数 × 平均单媒体大小
示例（保守）：200 帖/天 × 2.5 个 × 0.8MB ≈ 400MB/天
  30 天 ≈ 12GB    90 天 ≈ 36GB    180 天 ≈ 72GB
```

结论：MMVP 验证窗口（4-6 周）内 < 20GB，现有磁盘安全；**磁盘使用率 70% 告警即触发 COS 迁移评估**（§10 v2），不等到打满。若 DAU 爬坡导致日发帖数超模型 5 倍，提前启动迁移。

## 3. 前端架构

### 3.1 分层

```
pages/            视图层：WXML/WXSS/JS，只做渲染与交互
  ├── index / buddy / profile（3 tab）
  └── login / post-create / buddy-create / search
      / post-detail / buddy-detail / apply / buddy-applies
      / my-posts / drafts / messages / settings

utils/api.js      接口层（唯一后端依赖点，Adapter 模式）
utils/data.js     常量 + 种子数据（仅 LocalAdapter 使用）
utils/util.js     纯函数工具（时间格式化等，双 Adapter 共用）
styles/icons.wxss 图标库（构建产物）
app.wxss          设计系统（CSS 变量映射《视觉设计规范》）
```

### 3.2 核心原则：页面零感知后端切换

`utils/api.js` 对上暴露的接口签名在原型期即按"后端版"设计（见 §5.2），页面只调用 `api.getFeed()`、`api.applyToBuddy()` 等语义化方法。上线切换时新增 `HttpAdapter` 实现同一组接口，页面代码**一行不改**：

```js
// utils/api.js 顶层结构（目标形态）
const adapter = require('./adapters/http')    // 上线版
// const adapter = require('./adapters/local') // 原型版
module.exports = adapter                      // 接口签名不变
```

### 3.3 端侧状态与缓存策略

| 数据 | 策略 |
|---|---|
| 登录态 | JWT 存 storage（7 天有效期，见 §3.4 刷新契约） |
| 城市偏好 | storage（现有 `wudao_city` 保留） |
| 草稿 | **storage 本地持久化**（PRD 明确 v1 本地草稿够用）；发布成功即删 |
| 搜索历史 | storage 本地 ≤10 条（PRD 4.2a，不上云） |
| 信息流列表 | 每次冷拉取 + 页内游标分页（不缓存到 storage，避免与后端不一致） |
| 图标/静态资源 | 已烘焙为 WXSS data-uri，无网络请求 |

### 3.4 HttpAdapter 请求契约（401 单飞重试，防循环）

```
request(options, retried = false)
  ├─ 注入 Authorization: Bearer <token>
  ├─ 响应 401 && retried === false：
  │    → 进入刷新流程（单飞 single-flight）：
  │       · 全局仅一个 refreshPromise：
  │         并发多请求同时 401 → 共享同一次 wx.login + /auth/login
  │       · 刷新成功 → 各自重放原请求（retried = true）
  │       · 刷新失败 → 清除 token → 跳登录页
  ├─ 响应 401 && retried === true：
  │    → 不再重试，清除 token → 跳登录页   ← 硬性上限：重试 ≤ 1 次
  └─ 其余错误码按 §5.2 错误表处理
```

**两条铁律**：① 任何请求最多重放一次（`retryCount ≤ 1`），杜绝 401 → 重登 → 401 → 重登 死循环；② `refreshPromise` 全局唯一，并发 401 只触发一次 `wx.login`（微信登录接口有频率限制，且重复弹登录页是事故级体验）。

## 4. 数据模型设计（MongoDB：`wudao` database）

### 4.1 集合总览

| 集合 | 用途 | 读写特征 |
|---|---|---|
| `users` | 用户档案 | 读多 |
| `posts` | 内容帖（PGC+UGC 统一） | 读极多 |
| `buddy_posts` | 搭子帖 | 读多 |
| `applies` | 应征记录（**隐私核心**） | 写多 |
| `comments` | 评论 | 读多 |
| `reactions` | 点赞/收藏行为 | 写极多 |
| `messages` | 站内通知 | 读多 |
| `reports` | 举报 | 写少 |
| `uploads` | 媒体文件生命周期（防孤儿文件） | 写多 |
| `sessions` | JWT 会话（支持吊销） | 读写均衡 |
| `wx_tokens` | 微信 access_token 缓存 | 读写均衡 |
| `hot_searches` | 热门搜索词（运营配置） | 读多 |
| `track` | 埋点事件（TTL 90 天） | 写多 |
| `admin_audit` | 运营操作日志 | 写少 |

> 与 meetpoint 的 MongoDB 实例共机不共库：舞岛使用独立 database `wudao`，备份策略独立配置。

### 4.2 字段定义（关键字段）

```js
// users —— 注意：session_key 不落库（§6.1）
{ _id, openid, unionid,            // unionid 有则存（未来开放平台互通）
  nickname, avatarUrl, city,
  role: 'user' | 'admin',          // 权限角色（仅服务端授予，见 §5.4）
  accountType: 'personal' | 'official',  // 账号类型：official 承载 PGC 账号
  status: 'normal' | 'banned',
  stats: { postCount, buddyCount },
  postWindow: { count, date },     // 当日发帖数（限频）
  createdAt, updatedAt, lastActiveAt }

// sessions（JWT 吊销表：jti → 用户映射，登出/封禁时写入）
{ _id: jti, userId, expireAt }     // TTL 索引自动过期

// posts（PGC 与 UGC 同构，PGC 由 official 账号经 admin 接口发布）
{ _id, userId, kind: 'content',
  cat: 'outfit'|'recovery'|'culture'|'gossip'|'practice'|'class'|'ugc',
  title, body, images: [url], video: url, city,
  pinned: false,
  status: 'checking' | 'online' | 'removed' | 'deleted',   // 内容状态机（§4.5）
  mediaAudit: [{                   // 媒体审核状态机（§4.5）——一帖多媒体各自独立
    url,
    mediaType: 'image' | 'video',
    traceId,                       // mediaCheckAsync 返回，回调定位用
    state: 'pending' | 'pass' | 'fail',
    reason,                        // 违规原因（回调返回）
    checkedAt
  }],
  stats: { likeCount, collectCount, commentCount },
  createdAt, updatedAt }

// buddy_posts（MMVP 无状态机，手动标记）
{ _id, userId, kind: 'buddy',
  buddyType: 'practice'|'groupbuy'|'contest'|'other',
  title, body, images, video,
  city,                            // 城市名（如"北京"）
  location,                        // 用户主动选择并公开的活动地点名称（POI 名，
                                   //   如"朝阳大悦城"）——不含经纬度（§7 隐私定义）
  time, needCount,
  status: 'recruiting' | 'ended',  // 搭子状态机（§4.5）
  stats: { applyCount },
  createdAt }

// applies —— contact 是全库唯一敏感字段
{ _id, userId /* 应征者 */, postId, publisherId,
  message, contact,                // 微信号/手机号
  status: 'pending' | 'viewed',
  createdAt }
// 唯一索引 (userId, postId)：并发重复应征由数据库兜底（§4.3）

// comments
{ _id, userId, postId, content,
  status: 'checking' | 'online' | 'removed' | 'deleted',
  createdAt }

// reactions（行为表，防数组膨胀）
{ _id, userId, targetId, targetType: 'post',
  type: 'like' | 'collect', createdAt }

// messages —— targetType/targetId 前置，兼容 v1 圈子/关注/活动通知
{ _id, toUserId, fromUserId,
  type: 'system'|'like'|'comment'|'collect'|'apply',
  targetType: 'post'|'comment'|'buddy'|'user',   // v1 可扩展 'circle'|'activity'|'follow'
  targetId,
  snapshot,                        // 展示快照（如帖子标题，防原帖删除后无文案）
  content, read: false, createdAt }

// uploads —— 媒体生命周期（防孤儿文件打满磁盘，§6.7）
{ _id, userId, path,               // /data/wudao/uploads/2026/08/xxx.jpg
  mediaType: 'image' | 'video', size,

// temporary：已上传未引用 → 24h 后定时清理（物理删除）
// attached：被帖子引用；帖子软删 90 天物理清理时同步处理

// reports

  status: 'pending'|'resolved'|'dismissed', handledBy, createdAt }
```

### 4.3 索引设计（含排序方向；查询热路径优先）

| 集合 | 索引 | 支撑场景 |
|---|---|---|
| posts | `{status: 1, createdAt: -1}`（可加 `partialFilterExpression: {status: {$eq: 'online'}}`，仅索引线上内容，索引更小） | 信息流 |
| posts | `{city: 1, status: 1, createdAt: -1}` | 城市 tab |
| posts | `{cat: 1, status: 1, createdAt: -1}` | 分类筛选 |
| buddy_posts | `{status: 1, createdAt: -1}`、`{city: 1, buddyType: 1, status: 1, createdAt: -1}` | 搭子列表筛选 |
| applies | **唯一 `{userId: 1, postId: 1}`** | **并发重复应征数据库级兜底**（业务校验 + 唯一索引双保险） |
| applies | `{postId: 1, createdAt: -1}` | 发起人查应征列表 |
| reactions | 唯一 `(userId, targetId, type)` + `(targetId, type)` | 去重、计数、我的点赞列表 |
| messages | `(toUserId, read, createdAt)` | 未读数、消息列表 |
| uploads | `(status: 1, createdAt: 1)` | 孤儿文件扫描（status=temporary && createdAt < 24h 前） |
| sessions | TTL `expireAt` | 会话自动清理 |
| track | TTL `createdAt`（90 天）+ `(event, createdAt)` | 原始事件自动清理、按事件查询 |
| hot_searches | `(enabled: 1, weight: -1)` | 搜索页热门词列表 |

### 4.4 分页规范（正式契约）

**时间类型约定**：数据库统一使用 BSON `Date`；API 层 cursor 序列化为 **ISO 8601 字符串**（全局唯一选择，禁止 timestamp/Date 混用）。

```
排序键（全局统一）：createdAt DESC, _id DESC

游标查询条件（严格形式）：
  (createdAt < cursor.createdAt)
  OR
  (createdAt == cursor.createdAt AND _id < cursor._id)

请求：{ cursor: { createdAt: "2026-08-19T10:00:00.000Z", id: "66b3f0..." }, limit: 20 }
```

同一毫秒并发写入的数据由 `_id` 二级排序兜底，保证不重复、不漏条。

### 4.5 状态机设计（三层分离，禁止混用）

| 状态机 | 字段 | 取值 | 语义 |
|---|---|---|---|
| **内容状态** | `posts.status` / `comments.status` | `checking` → `online` → `removed` / `deleted` | **内容当前是否可公开展示**。checking = 审核未完成不可展示；online = 信息流可见；removed = 违规下架；deleted = 用户/运营删除（软删，90 天后物理清理） |
| **媒体审核状态** | `posts.mediaAudit[].state` | `pending` → `pass` / `fail` | **单个媒体文件**的审核进度。一帖多图各自独立（图1 pass、图2 fail、视频 pending 是合法状态） |
| **搭子状态** | `buddy_posts.status` | `recruiting` → `ended` | 招募中/已结束（手动标记或定时过期） |

**联动规则**（posts.status 由 mediaAudit 推导，服务端回调时原子更新）：

```
任一 mediaAudit.state == 'fail'    → posts.status = 'removed'（+ 通知作者）
全部 mediaAudit.state == 'pass'    → posts.status = 'online'
存在 'pending'（且无 'fail'）      → posts.status = 'checking'
```

`posts.status = 'checking'` 的语义**永远是**"内容不可公开展示，因审核尚未完成"，而不是"某个媒体在审核"——单媒体进度看 `mediaAudit`。

## 5. 后端架构（Express 服务）

### 5.1 模块划分（单服务，路由分域）

```
server/
├── app.js                 # Express 入口：helmet/cors/限流/错误中间件

├── db.js                  # MongoClient 单例（沿用 meetpoint 模式，database: wudao）
├── routes/

│   │                        PUT  /api/auth/profile（字段白名单，见 §5.2）

│   │                        GET  /api/content/posts/:id
│   │                        POST /api/content/posts        （先过 seccheck）
│   │                        DELETE /api/content/posts/:id  （软删，仅本人）

│   │                        POST /api/content/comments
│   ├── buddy.js           # GET  /api/buddy/feed?type&city&cursor
│   │                        GET  /api/buddy/posts/:id
│   │                        POST /api/buddy/posts

│   ├── search.js          # GET  /api/search?q=&cursor        （帖子+搭子帖统一搜索）
│   │                        GET  /api/search/hot              （热门词，内存缓存 5min）
│   ├── message.js         # GET  /api/message/list?tab / unread / read-all
│   ├── seccheck.js        # POST /api/seccheck/callback       （微信媒体审核回调）
│   ├── admin.js           # POST /api/admin/pgc-publish / remove / reports ...
│   └── upload.js          # POST /api/upload/image|video     （multer → uploads 生命周期）
├── services/
│   ├── wxapi.js           # code2Session / msgSecCheck / mediaCheckAsync
│   │                      #   + access_token 集中管理（wx_tokens 缓存，2h 提前 5min 刷新）
│   ├── audit.js           # 敏感词粗筛（本地词库 ~2k 条）→ 官方接口的分级调用
│   └── notify.js          # 站内 messages 写入 + 订阅消息推送（P1）
├── middleware/
│   ├── auth.js            # JWT 校验 + 用户加载 + 封禁拦截 + 吊销检查
│   └── rateLimit.js       # 按用户/按 IP 限频（发帖 60s/条、评论 15s/条、应征 30s/条、搜索 10 次/min）
├── jobs/                  # node-cron 定时任务（§6.6）
└── deploy.sh              # rsync + pm2 reload（沿用存量脚本模式）
```

**统一中间件链**：`helmet → 请求体白名单解析 → 限流 → JWT（写接口）→ 业务路由 → 全局错误处理`。所有响应统一 `{ code: 0, data } | { code, msg }`。

**`PUT /api/auth/profile` 字段白名单（P0 安全项）**：

```
允许：nickname, avatarUrl, city
禁止（服务端直接丢弃并记 admin_audit 告警）：role, status, accountType,
      _id, openid, unionid, stats, postWindow, createdAt
```

**统一错误码**：

| code | 含义 | 端侧处理 |
|---|---|---|
| 0 | 成功 | — |
| 401 | 未登录/JWT 失效/被吊销 | 单飞刷新重试一次，仍 401 则跳登录页（§3.4） |
| 403 | 越权（如非发起人读应征列表） | toast 提示 |
| 4101 | 内容安全检测不通过（文本） | 提示"内容含违规信息，请修改" |
| 4102 | 媒体审核不通过（异步撤回） | 通知 + 隐藏内容 |
| 4103 | 重复应征 | toast（现有文案不变） |
| 429 | 频率限制 | toast"操作太频繁" |
| 500 | 服务异常 | toast + 重试引导 |

### 5.3 防滥用设计

| 风险 | 措施 |
|---|---|
| 恶意刷帖 | 限流中间件：同用户发帖 ≥ 60s 间隔（users.postWindow 当日计数，上限 20 帖/日） |
| 刷应征/骚扰 | 单帖同用户仅一条应征（业务校验 + `(userId, postId)` 唯一索引**双保险**）；应征 30s 间隔；50 条/日上限 |
| 接口盗刷 | JWT 鉴权 + express-rate-limit 按 IP 双维度；请求体字段白名单 |
| access_token 泄漏 | 仅存服务端 `wx_tokens`，绝不下发；Secret 走 `.env`（chmod 600，不入库不入仓） |
| msgSecCheck 频率限制 | `audit.js` 本地敏感词粗筛，可疑再调官方接口，节省配额 |
| 媒体滥用 | multer 限制：图 ≤ 10MB（≤9 张）、视频 ≤ 100MB / 60s；扩展名白名单 |
| **孤儿文件打满磁盘** | uploads 生命周期：temporary → attached；24h 未引用物理删除（§6.7） |
| 上传目录穿越 | 文件名服务端重命名 `<uuid>.<ext>`，禁用原始文件名 |

### 5.4 权限模型与 admin 授予机制（P0 安全项）

**role 与 accountType 职责分离**：

```js
role:        'user' | 'admin'       // 权限角色：能做什么（进后台、删内容、处理举报）
accountType: 'personal' | 'official' // 账号类型：是谁（PGC 官方垂类账号 vs 普通用户）
```

MMVP 实际使用：`role ∈ {user, admin}` × `accountType ∈ {personal, official}`。未来扩展"舞室账号/老师账号/品牌账号"时只动 accountType 枚举，role 语义不变。

**admin 授予铁律**：

```
role = admin 只能通过以下两种途径授予：
  ① 服务器端初始化脚本（db.users.updateOne 直接写库）
  ② 已有 admin 调用 /api/admin/grant（记 admin_audit）
任何前端路径（含 PUT /api/auth/profile）均不可修改 role/status/accountType
（字段白名单在 §5.2 强制执行，越权字段直接丢弃并告警）
```

## 6. 核心流程时序

### 6.1 登录态（code2session + JWT；session_key 不落库）

```
小程序端
  → wx.login() 取 code
  → POST /api/auth/login { code, nickname, avatarUrl }
      服务端：
      ① GET code2Session(appid, secret, code) → openid, session_key(, unionid)
      ② openid 查找/建档 users（openid 唯一，幂等）
         · unionid 有则存（未来开放平台互通预留）
      ③ session_key 用完即弃，不写入 users，不做任何长期存储
         （MMVP 无需解密用户数据的场景；未来如需——如解密手机号——
           再设计 ≤5 分钟的内存级短期缓存，绝不入库）
      ④ 签发 JWT { uid, jti, exp: 7d }（HS256，secret 在 .env）
      ⑤ sessions 写 { jti, userId, expireAt }（支持吊销）
      → return { token, user }
  → 端侧 storage 存 token，后续请求 Authorization: Bearer <token>

静默续期：401 时走 §3.4 单飞刷新契约（重试 ≤1 次），对用户无感
```

### 6.2 发帖审核流（文本同步审核 + 媒体异步审核，全部通过才公开）

**与 v1.2 的关键变更**：放弃"先发后撤"，MMVP 采用 **checking → 全部通过 → online** 的稳妥方案（街舞内容含大量人像/视频，未审核媒体直接进信息流风险不可控）。

```
前置：媒体已上传（§6.7），拿到 uploads temporary URL
用户点发布
  → POST /api/content/posts { title, body, images, video, cat }
      ① 限流检查（60s 间隔 / 日限额）
      ② 文本 title+body → audit.js 敏感词粗筛
      ③ 可疑/全部 → wxapi.msgSecCheck(openid, content)        ← 同步
           不通过 → return 4101，前端提示修改（不发帖，媒体仍为 temporary）
      ④ 逐媒体调 wxapi.mediaCheckAsync(url, openid)            ← 异步
           · 媒体须公网可访问（https://meetpoint.top/wudao/u/...）
           · 返回 trace_id 逐个记入 mediaAudit[].traceId
      ⑤ posts 入库 status='checking'，mediaAudit[].state='pending'
         · 前端 toast："发布成功，审核中"
         · 「我的发帖」列表可见 checking 帖（带"审核中"角标）
      ⑥ 引用的 uploads 全部置 attached
  → 微信审核完成后回调 POST /api/seccheck/callback
      ① 验签（Token 校验，URL 配置在 mp 后台"消息推送"）
      ② 按 trace_id 定位 mediaAudit 条目 → 更新 state/reason/checkedAt
      ③ 按 §4.5 联动规则原子更新 posts.status：
           全部 pass → online（进入信息流，作者收"已发布"通知）
           任一 fail → removed（通知作者，含违规原因）

降级策略（预案，不默认启用）：若线上观测审核延迟 P95 > 10 分钟且成为常态，
经产品确认后可切换"先发后撤"（checking 期间即展示，fail 撤回）——切换点收敛
在回调联动规则一处，数据模型无需变更。
```

### 6.3 应征流（隐私红线落地）

```
应征者 B 提交
  → POST /api/buddy/posts/:id/apply { message, contact }
      ① 校验：帖 status=='recruiting'、B != 发起人、限频
      ② contact 经 msgSecCheck（防止把违规内容藏进联系方式）
      ③ 写 applies { userId: B, contact, ... }
         · 业务层先查重，插入若触发 (userId, postId) 唯一索引冲突
           → 捕获 E11000 → return 4103（数据库层兜底并发）
      ④ 写 messages 通知发起人 A（**通知内容不含 contact**）

发起人 A 查看
  → GET /api/buddy/posts/:id/applies
      ① JWT 解出 uid，校验 uid == 帖 publisherId  ← 隐私红线的服务端强制点
      ② 返回应征列表（含 contact）
      ③ 顺手将 applies.status 置 viewed

公开渠道（feed/detail）
  → 输出对象经过 pick() 字段白名单裁剪，contact 永不出现在响应里
```

### 6.4 消息通知

- **站内**：互动发生时写 `messages`（5 类：system/like/comment/collect/apply），带 `targetType/targetId/snapshot`；红点逻辑沿用
- **站外订阅消息（P1）**：授权按需请求——**用户执行需要通知的动作时**（应征、发布搭子帖），先判断对应模板是否已有有效订阅授权，无则 `requestSubscribeMessage` 请求该模板，服务端再发送；**不做"每次发帖都弹授权"**（弹窗疲劳会导致授权率崩塌）

### 6.5 搜索（PRD 4.2a）

**产品行为**：帖子 + 搭子帖统一搜索（不分类筛选），关键词匹配标题/正文/描述/位置/城市（舞种词天然出现在文本字段中）；结果按时间倒序混排，卡片用类型徽标区分；初始态展示搜索历史（本地 ≤10 条）+ 热门词（运营配置 6-8 个）；输入 ≤20 字，回车触发（v1.1 再做输入联想）。

**检索方案三段演进**（按数据量切换，接口契约不变）：

| 阶段 | 数据量 | 方案 | 说明 |
|---|---|---|---|
| MMVP | < 5 万文档 | **MongoDB regex 包含查询** | 单机毫秒级；无索引全扫也可接受 |
| v1.0 | 5 万 - 500 万 | **MongoDB text index** | `{title:'text', body:'text'}, {weights:{title:10, body:3}}`；中文分词效果一般但够用 |
| v2 | > 500 万 或需相关性/纠错 | Elasticsearch / Meilisearch | Docker 部署，change stream 同步索引；支持拼音/纠错/聚合 |

**服务端要点**（`routes/search.js`）：

```
GET /api/search?q=<kw>&cursor=
  ① 参数校验：q trim 后 1-20 字；超长截断；空 q 返回空集
  ② regex 转义：kw 中正则元字符全部 \ 转义（防 ReDoS / 注入）
  ③ 并行两查：posts(status=online) + buddy_posts，
     字段 = title/body（posts）｜title/body/location（buddy_posts）
  ④ 内存合并 createdAt 倒序 + 游标分页（复用 §4.4 契约）
  ⑤ 输出：卡片对象带 searchKind('post'|'buddy')，搭子帖带 typeColor/needLeft
  ⑥ 限频：单用户 10 次/分钟（重查询）

GET /api/search/hot
  hot_searches 集合读 enabled 词，按 weight 排序取 8 个；进程内缓存 5 分钟
```

**端侧要点**（已实现）：搜索历史本地 storage；`searchAll`（写历史）与 `searchOnly`（静默刷新，从详情页返回不重复记历史）分离。

### 6.6 定时任务（node-cron）

| 任务 | 频率 | 逻辑 |
|---|---|---|
| 搭子帖过期下架 | 每小时 | `time < now - 7d` 且 recruiting → ended |
| **孤儿媒体清理** | 每小时 | uploads status=temporary 且 createdAt < 24h 前 → 物理删除文件 + status=deleted |
| 统计汇总 | 每日 02:00 | track 聚合 → `track_daily`（长期保留）；原始事件靠 TTL 索引 90 天自动清理 |
| 数据备份 | 每日 03:00 | `mongodump --db wudao` → gzip → 本地保留 7 份 + 异机同步 |
| 软删数据清理 | 每周日 | status=deleted 且 updatedAt < 90d → 物理删除（含关联 uploads 置 deleted） |

### 6.7 上传链路（uploads 生命周期管理）

```
POST /api/upload/image|video（multer，JWT 必须）
  → 校验大小/类型/扩展名白名单 → 重命名 <uuid>.<ext>
  → 落盘 /data/wudao/uploads/yyyy/mm/
  → 写 uploads { status: 'temporary' }
  → 返回 { url, fileId }

POST /api/content/posts（或 buddy/posts）
  → 校验引用 url 属于当前用户 && uploads.status == 'temporary'
  → 创建帖子成功 → 引用的 uploads 置 'attached'

不发帖的媒体：
  temporary 挂满 24h → 定时任务物理删除（§6.6）
  → 用户可无限上传但永远发不了帖，磁盘不会被白嫖打满
```

## 7. 内容安全与合规架构

| 项 | 方案 |
|---|---|
| 文本检测 | `msgSecCheck`（需 openid），发布/评论/应征留言三入口统一走 `wxapi.msgSecCheck`，前置敏感词粗筛 |

| 密钥管理 | WX_APPID/SECRET、JWT_SECRET 全部走服务器 `.env`（chmod 600，不入 git） |

### 8.2 Nginx 增量配置（追加到现有站点）

```nginx
# 顺序与匹配符明确化：^~ 前缀匹配，最长优先
# /wudao/u/（静态媒体）必须先于 /wudao/（API）声明，语义更清晰
location ^~ /wudao/u/ {
    alias /data/wudao/uploads/;
    expires 30d;
    add_header Cache-Control "public";
}

location ^~ /wudao/ {
    proxy_pass http://127.0.0.1:3100/;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    client_max_body_size 100m;          # 视频上传
    proxy_read_timeout 60s;
}
```

**路径剥离规则（写给后来者的防坑说明）**：

> `proxy_pass` 结尾的 `/` 会剥离 location 前缀：外部请求 `/wudao/api/content/feed` → Express 实际收到 **`/api/content/feed`**。因此 **Express 内部路由统一使用 `/api/*`，业务代码中严禁再拼接 `/wudao` 前缀**（否则会出现 `/api/api/...` 或 `/wudao/api/...` 404）。

小程序后台 request/uploadFile 合法域名追加 `https://meetpoint.top`（已备案，当天生效）。

### 9.1 基础监控

### 9.2 业务埋点（track 集合：TTL 90 天自动清理，`track_daily` 聚合永久保留）

| 事件 | 触发点 | 支撑指标 |
|---|---|---|

## 附录 A：安全清单（Security Checklist）

- [x] SQLi/NoSQL 注入：MongoDB 查询参数化 + 请求体字段白名单；**拒绝 `$` 前缀键注入**（`$where`/`$$` 等过滤）；搜索关键词 regex 元字符转义（防 ReDoS）
- [x] RCE：无 shell 调用；上传文件重命名 + 扩展名白名单 + Nginx 静态目录禁执行
- [x] AuthZ：JWT + 路由级中间件；越权动作服务端校验（发起人身份、帖子归属、admin 角色）；**profile 字段白名单阻断 role 提权**（§5.2/§5.4）
- [x] XSS：WXML 数据绑定默认转义，无 rich-text 动态 HTML
- [x] SSRF：出网请求仅微信官方 API 域名（白名单硬编码于 wxapi.js）
- [x] 反序列化：不使用任何反序列化能力
- [x] 敏感信息：contact 仅存 applies；**session_key 不落库**（§6.1）；WX_SECRET/JWT_SECRET 仅存服务器 .env（600）
- [x] 传输：全链路 HTTPS（Let's Encrypt，certbot 自动续期）
- [x] 频控：发帖/评论/应征/搜索四级限频 + express-rate-limit IP 维度
- [x] 并发安全：applies `(userId, postId)` 唯一索引兜底重复应征；reactions 唯一索引兜底重复点赞
- [x] 存储滥用：uploads temporary/attached 生命周期 + 24h 孤儿清理
