# 街舞知识库设计（Dance KB）

状态：**仅设计，未开发**
定位：舞岛 PGC 生产线的**事实底座**——给 [`agents/dance-desk`](../agents/dance-desk/AGENT设计.md) 的 `fact-lock` 提供可查、可引、可追溯的结构化事实。
服务对象：v1 **仅内部**（Agent 检索 + 人工查阅），schema 预留对外字段，后续可编译成小程序词条页。
检索形态：**向量语义检索 + 关键词精确匹配的混合检索**。

> 本目录 `kb/` 与小程序代码分离，需加入 `project.config.json` 的 `packOptions.ignore`，不进小程序上传包。

---

## 0. 要解决的问题

`AGENT设计.md` §3 Skill 3 规定：新闻、历史、价格、名次、八卦「有补充信息或检索结果才允许写死数字」。但当前没有任何本地事实源，实际后果有三个：

1. **每篇重查**：同一个 KOD 创办年份、同一家舞室的价格，写一次查一次。
2. **查完即丢**：`articles/` 里 12 组调研的事实成果沉淀在文章正文里，无法被下一篇复用。
3. **口径漂移**：同一个专有名词，不同文章的注释措辞不一致；同一条传闻，这篇标「圈内流传」下篇可能写成既定事实。

知识库把「事实」从「文章」里剥离出来，成为独立的、带来源、带时效、可被检索的原子条目。

## 一、内容分层：五类实体 + 两类支撑

不按文章存，按**可复用的原子条目**存。

| 目录 | 实体 | 说明 | 冷启动目标 |
|------|------|------|-----------|
| `styles/` | 舞种 / 元素 | Breaking、Popping、Locking、House、Waacking、Krump、Voguing… | 12 |
| `people/` | 人物 | Don Campbell、Boogaloo Sam、Ness… 公开身份、代表作、争议关联 | 20–30 |
| `events/` | 赛事 / 组织 | KOD、BOTY、HHI、Juste Debout、SDF；创办年份、赛制、国内落地 | 15 |
| `studios/` | 舞室 / 场地 | 7 城测评已有沉淀；城市、主打舞种、价格区间（带采集日期） | 40+ |
| `terms/` | 术语 / 黑话 | Cypher、Toprock、Freeze、Bite、Jam、Battle… | 30 |
| `sources/` | 来源库 | 每条事实挂 `source_id`：URL、媒体、采集日期、可信度 | 随事实增长 |
| `disputes/` | 争议档案 | 八卦恩怨专用，三级标签落库 | 5–10 |

**术语库**是最被低估的一块。`AGENT设计.md` §2 要求「专有名词首次注释」，没有术语库这条规则不可执行——每次注释措辞都不一样。有了它，注释变成查表。

**争议档案**对应 fact-lock 的「已核实 / 圈内流传 / 不予传播」三级标签。目前这三级靠模型临场判断，落库后变成查表。`articles/2026-08-Popping绿坦Ness恩怨`、`articles/2026-08-街舞Sapo公开信息对照` 正好是首批素材。

## 二、存储形态：Markdown + YAML frontmatter

一条词条一个文件。不用数据库，理由：

- **人可读可改**——和现在写 `articles/` 是同一套习惯，不引入新工具
- **git 可 diff**——事实修订有历史，改了哪个年份、谁改的、什么时候改的一目了然
- **无需服务即可用**——Agent 直接读文件，构建与检索都是本地脚本
- **向量层是叠加而非替代**——frontmatter 天然是向量检索的元数据过滤字段

### 目录结构

```
kb/
├── 知识库设计.md            # 本文件
├── README.md                # 写作约定（P0 产出）
├── kb.config.json           # 嵌入模型、维度、复核周期等全局配置
├── schema/                  # 七类实体的字段定义 + 空白模板
│   ├── style.md  people.md  event.md  studio.md  term.md
│   ├── dispute.md
│   └── source.md
├── styles/  people/  events/  studios/  terms/  disputes/
├── sources/sources.yml      # 来源集中登记
├── tools/
│   ├── build.js             # md → _build/kb.json
│   ├── lint.js              # schema 校验 + 过期复核检查
│   ├── embed.js             # 增量嵌入 → _build/vectors.*
│   └── query.js             # 混合检索 CLI（Agent 调用入口）
└── _build/                  # 编译产物，git ignore
    ├── kb.json
    ├── vectors.bin          # Float32Array 紧凑存储
    └── vectors.meta.json    # chunk → entry 映射 + content hash
```

## 三、条目 schema

### 3.1 通用 frontmatter

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | ✅ | 全局唯一，如 `style-popping`、`studio-bj-caster` |
| `type` | ✅ | `style` / `people` / `event` / `studio` / `term` / `dispute` |
| `name_zh` / `name_en` | ✅ 至少一个 | 主名称 |
| `aliases` | 建议 | 别名数组，**关键词检索命中的主力字段**（绿坦、Sapo 这类靠语义召不回来） |
| `status` | ✅ | `verified` / `partial` / `disputed` / `draft` |
| `tags` | 选填 | 供检索与选题聚合 |
| `cities` | 选填 | 舞室/活动类必填，供元数据过滤 |
| `related` | 选填 | 关联 id 数组，构成词条网络 |
| `sources` | ✅（除 draft） | `source_id` 数组 |
| `updated` | ✅ | 最后修订日期 |
| `review_after` | 自动 | 由 `as_of` 字段与 `kb.config.json` 的复核周期推算 |
| `publishable` | 选填 | 预留对外字段，默认 `false`；未来词条页只取 `true` |
| `feed_category` | 选填 | 预留对外字段，映射到[内容导入模板](../docs/内容导入模板.md)的分类列 |

### 3.2 正文固定分栏

每条词条正文强制使用同一套小节，让 Agent 取用时不需要理解自由散文：

```markdown
## 一句话定义
（术语注释直接取这一段，保证全站口径一致）

## 已有共识
（可直接写死的事实，每条挂来源标记）

## 有争议
（存在多种说法，写作时必须并列呈现或回避）

## 不予传播
（涉隐私、未证实指控、未成年——写进库是为了让 Agent 明确知道「这块不能碰」，不是为了引用）

## 常见误会
（`AGENT设计.md` §4.3 文化历史体裁的「一个误会」直接取这里）

## 可延伸选题
（选题日历的输入）
```

「不予传播」栏是刻意设计的：只写「有共识的部分」会让 Agent 在遇到库里没有的敏感话题时，退回到自由发挥。明确标注禁区比留白安全。

### 3.3 易过期字段必须带采集时间

价格、课表、营业状态这类字段不能裸写：

```yaml
price:
  - { item: 年卡, value: 3800, unit: 元, as_of: 2026-08, source: s12 }
  - { item: 单次课, value: 120, unit: 元, as_of: 2026-08, source: s12 }
```

`lint.js` 按 `kb.config.json` 的 `review_months`（建议舞室价格 6 个月、赛事信息 12 个月）扫描，超期条目自动标 `待复核`，检索时随结果一并返回。

这条直接堵住 `AGENT设计.md` 里「禁止编价格」的漏洞——不是靠禁止，是靠给它一个可信且知道自己何时过期的价格。

## 四、检索层：混合检索

### 4.1 为什么不能只用向量

街舞领域大量短专有名词，纯向量表现很差：

- `KOD` 和 `HHI` 都是三字母赛事缩写，嵌入空间里几乎挨在一起
- 别名（绿坦、Sapo、Ness）语义上召不回对应词条
- 「北京 有没有 便宜 的 Breaking 舞室」需要的是元数据过滤（city + style + price），不是语义相似

所以是**四段式**：

```
查询
 → ① 元数据预过滤（type / cities / status，从 frontmatter 来）
 → ② 关键词精确匹配（name + aliases 命中直接置顶）
 → ③ 向量语义召回 top-k
 → ④ RRF 融合排序 → 按 entry 聚合
 → 返回：chunk 正文 + 完整 frontmatter + sources + 待复核标记
```

### 4.2 硬规则：向量层不提供数字

**向量检索只负责「找到哪条词条」，不负责「提供数字」。** 所有年份、价格、名次一律从 frontmatter 的结构化字段读取，不从召回的正文里摘。

这是 RAG 用于事实场景最容易翻车的地方：召回的段落被改写时数字会漂。结构化字段是原样透传的，不经过生成。

### 4.3 切块策略

词条本身很短且已经结构化，**按 §3.2 的小节切块**，而不是按固定字数。每个 chunk 携带 `entry_id`、`section`、`entry_name`。

嵌入文本前缀拼上词条名与别名，让短小节也有足够上下文：

```
[Popping / 波比 / 震感舞] 已有共识：……
```

### 4.4 规模测算与存储选型

预估 300 词条 × 平均 4 小节 ≈ 1200 chunk。1024 维 float32 约 **5 MB**。

这个量级**不需要向量数据库**。暴力余弦检索约 120 万次乘加，Node 里单次查询 5 ms 以内。存成 `_build/vectors.bin`（连续 Float32Array）+ `vectors.meta.json`。

超过约 5000 chunk 再考虑 `sqlite-vec`，届时只需替换 `query.js` 的召回段，schema 与构建流程不动。

### 4.5 嵌入模型选型

需要中英混写 + 大量专有名词。

| 方案 | 维度 | 优点 | 代价 |
|------|------|------|------|
| **阿里云百炼 text-embedding-v3**（推荐） | 1024 | 中文强、国内直连稳定、按量极便宜、零运维 | 需 API key，联网 |
| OpenAI text-embedding-3-small | 1536 | 生态成熟 | 国内网络需代理 |
| 本地 BGE-M3 | 1024 | 离线、免费、无 key | 需 Python 环境 + 约 2 GB 模型 |

模型与维度写进 `kb.config.json`。**换模型必须全量重嵌**，`embed.js` 检测到配置变更时强制全量。

### 4.6 增量嵌入

每个 chunk 存 `content_hash`。`embed.js` 只对新增和哈希变化的 chunk 调用嵌入接口。改一条词条的成本是一两次 API 调用，可以随手提交。

### 4.7 查询接口契约

Agent 通过 CLI 调用，输出 JSON：

```bash
node kb/tools/query.js "KOD 创办年份" --type=event --topk=5 --json
```

```json
{
  "query": "KOD 创办年份",
  "hits": [{
    "id": "event-kod",
    "name_zh": "KOD 世界街舞大赛",
    "status": "verified",
    "score": 0.91,
    "matched_by": ["keyword", "vector"],
    "section": "已有共识",
    "excerpt": "……",
    "facts": { "founded_year": 2004, "founder": "…" },
    "sources": [{ "id": "s07", "url": "…", "fetched_at": "2026-08-20" }],
    "stale": false
  }],
  "miss": false
}
```

`facts` 来自 frontmatter 结构化字段（可直接写死），`excerpt` 来自正文（仅供理解，不可作为数字依据）。`miss: true` 是 Agent 转外部检索的信号。

## 五、与 Dance Desk 接线

在 `AGENT设计.md` §5 工作流中插入两步：

```
用户主题 → Identity → category-router
    → kb-lookup（新增）
    → fact-lock（库中未命中才走外部检索）
    → 按体裁模板起草 → humanizer → anti-distill → image-brief → import-pack
    → kb-sync（新增）
```

### Skill 7 · `kb-lookup`

**触发**：`fact-lock` 之前，无条件执行。
**行为**：按主题与分类查库，返回命中词条。决策规则：

| 命中情况 | 处理 |
|---------|------|
| `status: verified` 且未过期 | 直接引用，`facts` 字段可写死 |
| `status: verified` 但已过期 | 措辞降级为「据 2026 年 8 月公开信息」，或触发外部复核 |
| `status: disputed` | 必须按「已有共识 / 有争议」并列呈现，禁止择一写死 |
| `disputes/` 命中「不予传播」 | 直接拒写该部分 |
| 未命中 | 走原 `fact-lock` 外部检索路径 |

### Skill 8 · `kb-sync`

**触发**：成稿后。
**行为**：输出 `===KB_PATCH===` 结构化补丁（新增词条或字段更新 + 来源），**写入待审目录，不直接落盘**。

不自动落盘是关键。知识库的全部价值来自可信度，一旦允许模型自动写入，几轮之后事实库就会被自己的幻觉污染，而且污染会被后续检索放大。人工 review 合并的成本很低，收益是这个库能长期可信。

没有 `kb-sync`，知识库会在建成三周后停止更新——这是这类项目最常见的死法。

## 六、冷启动

不从零手写，三步：

1. **回收存量**——`articles/` 12 组调研 + `utils/data.js` 45 篇种子内容里已核实的事实抽出来，预计 60–100 条，集中在舞室、赛事、人物。
2. **建骨架**——12 舞种 + 30 术语。共识度高、几乎不变、复用率最高，投入产出比最好的一批。
3. **增量沉淀**——Dance Desk 每出一篇，`kb-sync` 回写。

## 七、分期与验收

| 阶段 | 内容 | 工作量 | 验收 |
|------|------|--------|------|
| **P0** | 定 schema、建目录、写 `README.md` 约定、12 舞种 + 20 术语骨架 | 1–2 天 | 骨架条目全部通过 `lint` |

P2 之前 Agent 可以先用关键词检索接入，不必等向量层就绪。
